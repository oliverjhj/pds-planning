2. Issues introduced by the campaign's specific fixes
2.1 The pair-device step 6a audio_enabled logic almost certainly always returns false
Data-Arch §4.2: step 6 inserts the new devices row. Step 6a then queries "the count of existing active (non-newly-inserted) devices for this operator. If count = 0, set audio_enabled = true. If count ≥ 1, set audio_enabled = false." The phrase "non-newly-inserted" tells me the author saw the trap but a developer implementing this literally will write SELECT COUNT(*) FROM devices WHERE operator_id = $1 — which now includes the row from step 6. Count is always ≥ 1. Every first tablet defaults to audio_enabled = false. Combined with §2.2's column default of true, the row is inserted as true then immediately UPDATEd to false. Single-tablet operators ship with audio off, no audio plays, Reg 13 violated until somebody finds the dashboard toggle. The PRD claim that "operators deploying a single tablet require no configuration" (§5.2) is false in this implementation.
Even if the developer reads the parenthetical and adds AND id != $new_row_id, you also have the concurrency case: two pairings to the same operator within ~ms see each other's pre-state and both get audio_enabled = true. There is no uniqueness constraint backing the "exactly one audio device" rule (see also §3.1 below).
Fix direction: count before inserting and pass the result into the insert, or use the column's DEFAULT and only set false in 6a when count > 0 of prior rows. Add an integration test that pairs the very first device and asserts audio_enabled = true.
2.2 Heartbeat split has a hole between the two paths
Data-Arch §7.7 and PRD FR-AT-64: the foreground-GPS-service Handler loop runs only during an active journey. WorkManager runs when idle/backgrounded. There is a third state — app foregrounded, route list visible, no journey yet — that neither path covers. The driver powers the tablet on, looks at routes, considers the day, picks a route. That's 30–120 seconds. The journey-path service isn't running; the idle-path WorkManager might also have been scheduled to tick later. After 5 minutes of this, a healthy in-service tablet appears offline. The Data-Arch §7.7 closing line ("Fleet managers should interpret idle tablets as 'not in service'") concedes the WorkManager-failing case but does not concede this case. It will be the most common false-offline pattern.
The "two-path" framing is also a leak: there's a third path (foreground-non-journey) implicit in the architecture but unowned. Either fold it under the Handler loop (lifecycle-aware, run when Activity is in RESUMED state too), or let WorkManager be the unconditional baseline and let the GPS service add reliability during journeys.
2.3 The render-route-audio pipeline has not been sanity-checked for cost, latency, or feasibility
PRD §11.2 elevates "Server-side TTS API (e.g., Google Cloud Text-to-Speech)" to a hard dependency. Data-Arch §4.6 says the Edge Function makes one TTS call per stop plus one for the route announcement. The campaign treats this as small; it isn't:

Latency: Google Cloud TTS averages ~1–2s per request for short text; cold starts and queueing make 3–5s common. A 15-stop route is 16 sequential calls. Run serially: 30–80 seconds wall clock. Supabase Edge Functions on the free tier have a ~25s execution cap; paid plans extend to a few minutes. Long routes on free tier will time out. Long routes on paid tier with bad luck on TTS API will time out. Parallel calls would help but the doc doesn't say to parallelise; if many operators save routes simultaneously, parallel TTS calls multiply.
No idempotency or concurrency control: §4.6 says "Overwrite any existing files." If an operator clicks Save, then immediately edits and Saves again, two invocations race against the same six Storage paths. The "Save 1" rendering of stop_3.mp3 may land after the "Save 2" rendering of stop_4.mp3. Tablets end up with a mixed batch — half from Save 1, half from Save 2 — and route data inconsistent with audio. Needs a version key in the Storage path (e.g., include route.updated_at epoch) or a cancellation mechanism.
No re-render trigger except "re-save": §4.6 says failures resolve via "manual re-save of the route, or an admin-triggered re-render." There is no admin-triggered-re-render described anywhere. The operator's only recourse is to edit a stop, save, edit it back, save again — burning two TTS bills and propagating two FCM pushes and two full audio re-downloads to every tablet in the fleet.
Cost discipline: §11 Audio outdating ("all audio files for that route are re-downloaded regardless of whether they already exist locally" when the route appears in get_routes_since) means any field-only edit — change the direction label or route_number — triggers full TTS re-render (every stop) and full tablet re-download. A content_hash per stop, computed from route.name + last_stop.stop_name and next_stop.stop_name respectively, would let render-route-audio short-circuit unchanged stops. None of this is in the doc.
No TTS provider selected, no voice locked: §4.6 lists "Google Cloud Text-to-Speech, Amazon Polly" as alternatives. A "single configured voice" is required for consistency. The voice has not been chosen. Compliance argument (Reg 13(4), 300–3000Hz) explicitly rests on this voice being "selected and verified by the developer before deployment" — this is a real, pending work item the doc treats as future tense ("not assumed", "must be verified"). Until that work happens, Reg 13(4) is unfulfilled by spec.
TTS API key management not specified: where does the API key live? Edge Function secrets is the answer but the doc doesn't say.
Storage cost: ~50KB × 10 stops × 50 routes × 100 operators ≈ 2.5GB; Supabase free tier is 1GB. Paid is cheap but real, and unconstrained growth (audio files for soft-deleted routes never cleaned up — §6.4 only cleans tablet-side).

Fix direction: prototype the render Edge Function against a 15-stop route end-to-end before committing the architecture. The campaign called this "a small change" but it's a separate distributed system.
2.4 The FCM-then-render race
Data-Arch §8.4 diagram shows FCM push fired by the routes-updated trigger in parallel with the dashboard async-calling render-route-audio. FCM is fast (sub-second). The render is slow (tens of seconds). The tablet receives FCM, syncs route data immediately, then attempts audio download. The audio files don't exist in Storage yet. Audio download silently fails (per §7.4 step 4: "non-fatal"). Sync completes successfully, sync_status = 'synced', but the tablet shows "Audio not ready — syncing." Next FCM trigger won't fire (no route change has happened). The 30-minute periodic will eventually retry. So a freshly-saved route is unstartable for up to 30 minutes after the dashboard says it's ready.
Fix direction: either fire FCM only after render-route-audio reports success, or fire two FCM pushes (one for route data, one for audio-ready), or have the tablet poll Storage on failure with backoff. None of these are in the doc.
2.5 last_synced_with_return divergence warning will fire on every edit
FR-WD-12: warning fires when updated_at > last_synced_with_return. The routes table trigger (§3.5) sets updated_at = now() on every UPDATE. last_synced_with_return only updates on "Re-generate return." So after the first edit of either route post-generation, updated_at > last_synced_with_return is permanently true until regeneration. The operator gets the warning every single time they save the route (even on a trivial direction-label tweak). Warning fatigue → operators learn to dismiss it without reading → the mechanism is worth nothing.
Fix direction: probably "compare structural fields" (stop list or its hash) at save time, not just updated_at vs a baseline. Or set last_synced_with_return = now() on any save where structural content didn't change.
2.6 The two-stop look-ahead's accuracy gate evaluates the "wrong" stop
PRD FR-AT-13: "GPS accuracy gate: ... compare this estimate to the current target stop's proximity_radius_meters value." Then: "Two-stop look-ahead: ... each evaluated against its own proximity_radius_meters value." Reading these together — what's the gate value when monitoring N and N+1? The doc says "compare to the current target stop's" radius — implying one gate. But the two stops may have different radii. A fix that's accurate enough for stop N (200m radius) but not for stop N+1 (100m radius) gets through the gate, then triggers a look-ahead announcement for N+1 with insufficient accuracy. Or vice versa. The look-ahead path may misfire because the gate was set by the other stop.
I think the intent is "use stop N's gate to consider stop N detection; use stop N+1's gate to consider stop N+1 detection" — but the doc says "the current target stop's" with no clarification of which is current when both are being monitored.
Fix direction: explicitly state per-stop gating evaluation: the same fix passes the gate for stop N but not for stop N+1 if their radii differ; detection for each must be evaluated independently.
2.7 Audio-enabled tablets still download audio they'll never play
There's nothing in §7.2 step 7, FR-AT-28, or §6.4 that says "skip audio download if audio_enabled = false." A display-only tablet on the same operator account dutifully downloads every stop_N.mp3 for every route on every sync. On a fleet of 5 tablets, 4 of them waste storage and network. Not a bug per se, but a wasted-bytes oversight that becomes visible at scale (one operator's edit triggers 4× the cellular data it should).

3. Hidden assumptions
3.1 "Exactly one audio device per bus" is honor-system
PRD §5.2 and Data-Arch §2.2 implement audio designation as a per-device flag. The system has no concept of "bus." devices is scoped only to operator. So there is no constraint preventing:

Two devices on the same physical bus both with audio_enabled = true → two speakers playing the same MP3 with ~100–500ms offset → fails Reg 12(1)(b) consistency, which the campaign claims this very mechanism fixes.
A single-tablet operator with audio_enabled = false on their only device → no audio at all → fails Reg 7, 8, 9, 11, 12, 13 simultaneously.
An operator with 10 tablets all audio_enabled = true (forgot to toggle) → 10-speaker chorus.

The dashboard fleet view UI is supposed to be the safeguard but nothing prevents it. There's no warning like "this is your only device and audio is off." There's no per-bus grouping. The compliance argument in the Matrix for Reg 12(1)(b) ("single primary audio tablet per bus... audio_enabled flag prevents overlapping audio") describes intended behaviour, not enforced behaviour. The fix the campaign delivered is a soft default plus an operator-facing toggle, not a constraint.
Fix direction: either introduce a vehicles table and enforce one audio device per vehicle, or accept that "exactly one per bus" is an operator concern and rewrite the Reg 12(1)(b) compliance argument to be honest about that. The current Matrix wording is overconfident.
3.2 The custom access token hook is a single point of failure with non-obvious failure modes
Data-Arch §3.4a: custom_access_token_hook runs on every JWT issuance — login, refresh, Admin API session creation. It is SECURITY DEFINER and reads from devices and operators. Failure modes the doc doesn't address:

Hook throws an exception (a slow operators query during DDL, a network issue inside the function): every login and every JWT refresh fails. The whole product is down. Not just one operator — all of them.
Hook returns claims missing operator_id (e.g., a freshly-signed-up operator before the trigger has inserted the operators row, or a device whose devices row was deleted mid-session): the JWT is technically valid but every RLS-scoped query fails silently (per the Dashboard CLAUDE.md gotcha — "Supabase RLS errors are silent"). The user sees a working dashboard that returns empty everywhere.
Hook performance: every refresh does two indexed lookups. Fine. But every Edge Function getUser() also issues a fresh token check. At scale this is a hot path.

The RLS policies exclusively depend on this hook running correctly. There's no fallback path (e.g., RLS that joins through to verify if a claim is missing). One broken deploy of this function locks everyone out.
Fix direction: monitoring on the hook execution; one alarm metric for "JWT issued without operator_id claim and user has a corresponding row"; and probably a staging-environment integration test that catches signature drift between hook output and policy expectations.
3.3 Anonymous Supabase Auth users accumulate forever
Every pair-device call creates a new anonymous auth user. Every deregister/deactivate leaves the auth user behind (only devices.status flips to inactive). Over years this is unbounded auth-user growth. Supabase's auth-user limits and MAU billing are not addressed in any document. Probably fine at MVP scale; would be a real concern at any scale.
3.4 Tablets ideally feature 'battery protect' mode (PRD §11.1 assumption 10)
This is a hardware assumption with no enforcement. PRD §11.1 lists it as an "ideal" requirement. Without it, tablets continuously screen-on with FLAG_KEEP_SCREEN_ON (FR-AT-53) plus charging produce battery swelling within months. Operator returns dead tablet, you have a warranty claim and a confused operator. No "minimum supported device" list specifies which models meet this. Realistically a real risk for the small-operator market the product targets — they'll buy the cheapest Android tablet they can.
3.5 GMS-certified-tablet assumption (PRD §11.1 assumption 9)
Hard dependency on FusedLocationProviderClient and FCM, both of which require Google Mobile Services. Many cheap Chinese-brand tablets popular at the £150 price point are AOSP/non-GMS or have GMS removed. Operators buying the cheapest tablet on Amazon may not realise their tablet doesn't qualify. No mechanism in the app to detect GMS presence at first run and warn ("This tablet does not have Google Mobile Services. The PDS will not function correctly. Please use a GMS-certified device."). The compliance argument for Reg 9 timing (per Compliance Note 6) implicitly depends on this assumption being met by the operator.

4. Missing scenarios
4.1 Operator suspended while bus is mid-journey
FR-AT-60 and §6.1: the suspension status arrives via sync. The doc doesn't say what happens if is_active = true in journey_state when the suspended status hits. Strict reading of FR-AT-60: "disables all journey functionality" — does the running journey terminate mid-stop with passengers aboard? Audio just stops? Tube map freezes? §6.1 says journey continues offline regardless of dashboard state, but it doesn't address what happens on receipt of the suspension during an online journey. This is the most plausible adversarial scenario: operator misses a payment, gets suspended, has buses on routes right now. Behaviour is unspecified.
Fix direction: explicitly state — "operator suspension is honoured at journey end, not mid-journey" — and update FR-AT-60 to suppress lock-screen if journey_state.is_active = true.
4.2 Journey state recovery from an arbitrarily old crash
FR-AT-18 / NFR-R-05: "If the app is killed during an active journey, the journey state is recovered on next launch." The journey_state row has journey_started_at but no rule says "discard state older than N hours." So: bus parks at the depot overnight, the OS kills the app at 2 AM. Driver boots tablet at 8 AM. App finds is_active = true, resumes a stale journey from yesterday with current_stop_index = 7. No GPS movement matches stop 8 of yesterday's route. Auto-timeout at final stop won't fire (not at final stop). Driver is greeted with the journey screen showing a route they were never planning to run today. They figure it out (probably) and end the journey manually, but the recovery is wrong-by-default rather than correct-by-default.
Fix direction: at recovery, check now() - journey_started_at. If > N hours (8?) and no recent journey_event, clear state.
4.3 Pairing recovery user experience for a driver
FR-AT-04: if recover-device fails, "the app shows a clear message and returns to the first-run setup screen for re-pairing." Now consider: tablet sat unused for two months while the bus was in service repair. Driver gets in on a Monday morning at 8:55 AM for a 9 AM service. JWT refresh fails (expired). recover-device called. For any reason — Supabase outage, FCM-equivalent transient blip, rate-limit consumed by a prior glitch, even just IP-block from sharing a 4G IP with another rate-limited tablet — fails. Driver sees the first-run pairing screen. The driver does not have a pairing code. The driver does not have access to the dashboard. The driver has to phone the operator to phone the fleet manager to phone the bus depot to get someone to log in and generate a code, while passengers wait. Then the rate limit (5 attempts/hour per Android ID, lockout 15 minutes after 3 failures) means a couple of bad type-ins lock the tablet for 15 minutes.
The recovery is silent (good for the happy path) and catastrophic on failure (no graceful retry, no "offline mode for the next hour using cached JWT", no offer to call the operator).
Fix direction: distinguish transient failures (5xx, network errors) from terminal failures (device deactivated, secret mismatch). On transient failures, retain the cached JWT — if the cached JWT is still cryptographically valid (just past refresh window), keep using it; the worst case is the device makes an authed query against a JWT the server will reject, in which case fall back gracefully. On terminal failures only, show the pairing screen. Add visible "Pairing recovery in progress" UI rather than silent action.
4.4 Render-route-audio partial failure across stops
Doc says "if the TTS API call or Storage write fails, the function returns an error." Singular. But the function is a loop over stops. If stop 7 fails, what about stops 0–6 (already written) and 8+ (not yet attempted)? Are the partial files left in Storage? Tablets will then download files for stops 0–6 but not 8+, and the journey-start gate will fail until somebody re-saves the whole route, at which point all files are re-rendered and re-uploaded (wasted spend on 0–6).
Fix direction: render-route-audio needs explicit per-stop retry, partial-progress reporting, and idempotent resumption — or it needs to be a Postgres-job-style background worker with state, not an Edge Function.
4.5 Diversion announcement after recovery
A diversion was triggered mid-journey (stops 5-7 skipped, audio chime + diversion_start.mp3 played, journey_skipped_stops populated). App crashes at stop 4. Recovery: journey_state.current_stop_index = 4, journey_skipped_stops still contains [5,6,7]. The GPS state machine resumes, correctly skips 5–7. But passengers who boarded between crash and recovery don't hear the diversion announcement — it's not replayed on recovery and there's no visual indication on the tube-map that a diversion is currently active beyond the strikethroughs. A passenger who boarded at stop 4 sees stops 5,6,7 strikethrough'd with no audio context.
Fix direction: on recovery, if journey_skipped_stops is non-empty, replay the diversion start announcement (FR-AT-25) before resuming GPS monitoring.
4.6 WorkManager idle heartbeat killed and never recovers, operator deactivates device
Foreground-service heartbeat protects the journey window. Idle WorkManager doesn't on hostile OEMs. Tablet sits idle through a non-service period of a week. Operator decides to retire that tablet from the fleet (deactivate). On reactivation attempt (tablet pulls out for next service), the tablet has stale last_seen_at, the operator-side devices.status = 'inactive'. The driver boots the tablet, it tries to sync, gets back "device deactivated" → first-run pairing screen. The driver has the tablet that was working last week, now it's blank. Recovery requires fleet manager to generate a new pairing code and re-pair. The operator never gets a "your tablet has been offline for X days, is this expected?" prompt on the dashboard before deactivating — the dashboard's deactivation UI (FR-WD-17) doesn't have any inactivity-correlation check.
4.7 journey_events disk pressure
FR-AT-63: "Logs older than 30 days are auto-deleted on app startup." If the tablet doesn't restart (kiosked, foreground service, no reboots, no app crashes), the cleanup never fires. journey_events grows monotonically. Six months of in-service operation could be tens of thousands of rows. Doc doesn't specify cleanup outside startup.
Fix direction: run cleanup on each journey start as well.

5. Architectural smells
5.1 The two status columns are different state machines under the same name
operators.status is the three-state enum (pending / active / suspended) — campaign Task 4. devices.status is two-state (active / inactive) — original. Same column name, distinct semantics. Cross-references in code will be ambiguous. Worse, devices.status doesn't have a CHECK constraint while operators.status does — so a developer who doesn't read carefully could set devices.status = 'suspended' (no constraint to stop them) and break every status comparison silently. The recover-device function (§4.3) does both checks back-to-back with subtly different phrasings: "Reject if devices.status = 'inactive' or if the linked operator has status != 'active'." The asymmetric phrasing is a code-review hazard. A future reader writes if (devices.status == 'inactive' || operators.status == 'suspended') and misses the pending case.
Fix direction: rename one. devices.lifecycle_state or devices.activation_state. Add CHECK constraints to both.
5.2 Hard route deletion (§10) breaks tablet sync
§10 says routes "could be hard-deleted after 90 days (operations decision)." devices.active_route_id is set to NULL via ON DELETE SET NULL — campaign fix #28, which solves the FK constraint side. But the sync side is unfixed: get_routes_since (§4.5) returns routes where updated_at > p_last_ts. A hard-deleted route doesn't exist, so it isn't returned. Tablets that synced before the hard-delete still have the route locally, with no tombstone arriving to mark it deleted. The route stays in the local route list indefinitely; if the driver starts it, the tablet operates from a route the server has no record of.
Fix direction: either don't hard-delete (deletion stays soft for the product's lifetime), or implement a tombstone table that survives routes deletion, or have the deletion bump some sync-version cursor that tablets reconcile against.
5.3 The "two-path heartbeat" is leaky
See 2.2 above. Three states exist; only two paths cover them. Renaming the paths might help: "in-service path" (foreground service) and "out-of-service path" (everything else) is more honest. WorkManager isn't really "idle" — it's "everything that isn't an active journey."
5.4 The render-route-audio Edge Function is doing too much
It's reaching out to a third-party API, doing significant I/O (16 sequential calls), writing to Storage, with no explicit retry, idempotency, or partial-progress model. This is a job queue's job, not an Edge Function's. The campaign categorised this as a small architectural addition; it's actually a distributed-system addition.
5.5 RLS subquery on route_stops
§3.4 acknowledges that route_stops RLS uses a subquery into routes because route_stops doesn't carry operator_id. "O(1) lookup, not a full join" — true. But every per-stop read goes through this subquery. For a route-load endpoint that selects all stops for a route (the common case), the planner should hoist it but it doesn't always. Worth measuring with EXPLAIN; the route load is on a critical path for both dashboard render and tablet sync.
Fix direction: denormalise operator_id onto route_stops. The doc cited deliberate avoidance of this but didn't justify it; the cost of denormalisation is one extra column that's set by the dashboard at creation alongside everything else it already copies.

6. Compliance gaps
6.1 The alert is visually shown before the audio plays
PRD FR-AT-65 spec: "Timing: Fires at the same instant as the chime starts playing. The announcement overlay text (FR-AT-38) appears immediately after the 500ms flash, while the chime audio is still playing." So:

t=0: chime audio starts, visual flash starts
t=500ms: flash ends, announcement overlay text appears
t=~800ms: chime audio ends, announcement audio file starts

This means the visual announcement is present and readable while the audio chime is still playing — and the audio announcement hasn't started yet. The visual content leads the audio content by ~300–500ms. For a hearing passenger watching the screen, the text says "Diversion in progress" while the chime is still bleeping. For a deaf passenger, only the flash registers as the alert; the text appears immediately and they read it. Probably fine. But the Compliance Matrix's Reg 12(1)(b) consistency argument ("consistent with one another") doesn't address temporal alignment. A reasonable Reg 12(1)(b) reading would be that the audio and visual messages start at the same time. They don't.
6.2 The multi-tablet flash doesn't help rear hearing passengers
FR-AT-65 visual flash fires on every tablet. The audio chime fires only on the audio_enabled tablet. A hearing passenger in the back of the bus looking at the rear tablet (display-only) sees the flash, hears the chime faintly or not at all depending on speaker placement, then sees the announcement text. They get a partial alert — the visual half. This is arguably compliant (Reg 8(2)/10(2)(b)/11(2)(b)/11(5)(b) requires "an alert" — visual flash satisfies one component). But the Matrix's claim that FR-AT-27 and FR-AT-65 "together constitute the combined alert" suggests both are required; on the rear tablet, only one is delivered.
6.3 Reg 13(4) is conditional, not delivered
Matrix Reg 13(4): "selected and verified by the developer before deployment (not assumed)... rendering pipeline can be measured with audio analysis tools during development to confirm compliance." This is a TODO described as a guarantee. The voice has not been chosen. The verification has not happened. Until both happen, Reg 13(4) is unfulfilled. The Matrix is forward-stating compliance that will be true if the developer follows through. Worth flagging explicitly in the Matrix as "BLOCKING WORK — voice selection and frequency verification required before production deployment."
6.4 Driver-panel non-occlusion (FR-AT-40) in portrait
FR-AT-40 says "the panel occupies the lower portion of the screen... while the passenger information area (top two-thirds: route name, direction label, large next-stop name) remains fully visible above the panel at all times. This constraint applies in both portrait and landscape orientations."
In portrait, "lower one-third" of a 10-inch portrait tablet is ~5 inches of vertical space. The driver panel needs diversion buttons, H&R buttons, repeat-last, volume, end-journey, scrollable stop list (FR-AT-42). That's a lot in 5 inches. Either the panel will be cramped to the point of unusable touch targets (FR-AT pinch-points for gloved drivers, per persona 2.1), or it'll overflow into the top two-thirds and violate the constraint. The spec asserts the constraint without showing the panel design can satisfy it in portrait.
6.5 Reg 14(3)(b) (rear-facing wheelchair spaces) needs visible-at-the-back
Compliance Note 4 says additional tablets cover this. The audio_enabled mechanism means a rear tablet is display-only. Reg 14(3)(b) is about visibility, so display-only is fine. But: the rear tablet's GPS may detect stops independently of the front tablet (each tablet has its own GPS service). If the rear tablet's GPS lags or is unable to read accurately (poor reception at the back), the rear tablet's display state may differ from the front. A rearward-facing wheelchair user looks at the rear tablet and sees a different next-stop than the front tablet shows. Reg 12(1)(b) consistency concern across the same announcement at the same time.

7. Executability gaps — building strictly from these docs
7.1 rate_limit_attempts table doesn't exist in the schema
§4.2 and §4.3 reference "Tracked in a rate_limit_attempts table (or Edge Function KV store)." It's referenced and parenthesised away. Neither option is specified. A developer building from these docs will stop here and need a decision.
7.2 No TTS provider / voice / configuration
§4.6, §11.2, NFR-A-02, Reg 13(4) — all defer the choice. The decision is non-trivial (cost, latency, quality, voice availability, API stability, regional support, billing exposure). Until decided, the audio system can't ship.
7.3 No render-status surface
Dashboard has no UI for "is audio rendered for this route?" After save, operator clicks back to route list — route appears immediately (§4.4 says so). Nothing indicates rendering in progress. If it fails, operator never finds out unless they call a fleet manager who calls a driver who reports "audio not ready." For a regulated product this is invisible.
7.4 No FCM payload schema
Data-Arch §7.6: "Sends an FCM message to each device's FCM token, with a simple payload signalling 'routes have changed.'" "Simple payload" — what shape? Just a notification, or a data-only message? FCM behaviour on Android differs sharply (data-only wakes the app; notification-with-data shows a system notification when the app is backgrounded). For a kiosked app this matters. Not specified.
7.5 No mock GPS / test fixture strategy
Verification ritual (WORKFLOW §5.2) says compliance features are tested on a real device with "at least one failure case (GPS lost mid-journey, Bluetooth disconnects, sync fails, etc.)" — but the developer is in Kirkmere and the bus is hopefully running on a real route somewhere. Manually triggering GPS loss in a real journey is hard. There's no mock LocationProvider injection mentioned. The whole GPS state machine — two-stop look-ahead, H&R boundary detection, diversion skip, accuracy gate — needs a way to be exercised at the desk. None is described.
7.6 Custom access token hook setup is operationally fragile
§3.4a shows the SQL. But there's no description of how it gets registered in Supabase Auth (it's a console action in the Supabase dashboard, not a migration). It's not in the database — it's in Auth config. Easy to miss when standing up a new staging environment. Easy to lose if the hook is deleted manually. Reproducing the prod auth in staging requires a manual click in two places.

8. Internal contradictions
8.1 Android CLAUDE.md vs frozen docs — see §1.
8.2 §11 Implementation Notes ("Audio file outdating") vs cost-conscious sync
§11 says re-download all audio for any route in the sync response. §7.4 step 4 says audio download is non-fatal. So the tablet, every sync, has to re-attempt downloading audio for every changed route — even if only direction was changed. Wasted bandwidth, wasted Storage egress costs. Doesn't align with cost-conscious posture elsewhere.
8.3 PRD §1.4 "active if synced in last 30 days" vs Data-Arch §10 "could be auto-deregistered after extended inactivity (operations decision)"
These are not coordinated. Billing says "30-day sync window." Deregistration policy is "operations decision." Which side wins if they diverge? If billing requires sync-in-30-days and a tablet has been offline for 25 days (still billable) and operations chooses 30-day-deregister, the operator gets billed for a tablet they thought they were rid of for half a month.
8.4 WORKFLOW §13 "frozen documents" vs the seven-task campaign
WORKFLOW §13.4 Case 1 says re-planning is rare ("If it happens more than once or twice during the build, the planning was insufficient and we should pause for a more thorough re-plan"). The campaign was a seven-task re-plan covering structural rewrites of all four frozen documents — and it happened before the build. The doc handles this fine implicitly (the frozen rule re-engages after the campaign per CONTEXT.md line 161). But Round 2's findings will (if you act on them) constitute another re-plan. The cumulative reading of WORKFLOW §13.4 — Round 1's seven-task campaign + Round 2's likely follow-up + CLAUDE.md staleness fixes — suggests planning was indeed insufficient and the right move is one consolidated re-plan rather than three. The doc's tolerance for re-planning is the only thing keeping the project honest here, but it's also a fig leaf that allows the campaign to be framed as "complete."
8.5 CLAUDE.md Android, line 28, says "Audio: Android MediaPlayer for pre-rendered MP3 files"
Good — that's v3.3-aligned. But line ~96 still has the NaPTAN bundle. So the same file is partly v3.3-aligned and partly pre-v3.6. The CLAUDE.md was updated for Task 3 (audio) but not for Task 6 (scope cuts). Same conclusion as §1, sharpened.

9. Observability and operational reality
9.1 No production observability
journey_events are local (FR-AT-63, §5.4). When a tablet on a real route misses an announcement, nobody outside the bus knows. Fleet manager sees last_seen_at and active_route_id — that's the entire fleet-view payload. They don't see:

AUDIO_FILE_MISSING in the last hour
GPS_LOST in the last 10 minutes
STOP_PASSED_WITHOUT_DETECTION events
AUDIO_PLAYBACK_ERROR events
The number of manual stop advances (a proxy for GPS accuracy issues)

This is dim. For a regulated product whose compliance argument depends on the audio playing correctly, having no visibility into whether the audio is actually playing is a real problem.
Fix direction: a minimal journey_events_summary upload at journey end (counts only, no PII) gives the operator and the system administrator hindsight without violating offline-first.
9.2 No crash telemetry
No mention of Sentry, Crashlytics, or any crash-reporting SDK. If a tablet crashes mid-journey on a real bus, the developer hears about it only if the operator complains. The previous build's fatal Room schema crash — caught when run on the tablet — is exactly the kind of thing telemetry would catch industrial-strength.
9.3 No dashboard-side audit log
Operator changes a route stop. Tablet starts announcing the wrong stop. Operator denies they made the change. There's nothing in the schema recording who-changed-what-when on routes — routes.updated_at is the only audit signal. No history table, no event log. For a regulated product with multi-stakeholder content (fleet manager → driver → passenger), this seems thin.
9.4 No "render-route-audio failures" surface
If render-route-audio fails for a route, where does that get reported? §4.6 says "the dashboard may log this but does not surface it." So the failure is invisible. The operator's first signal is a driver complaint. There's no dashboard-side "routes whose audio failed to render" list.

10. The "is it executable" question, honestly
A developer building strictly from these seven documents would, by my count, hit the following blockers before delivering Stage 1:

CLAUDE.md tells them to bundle NaPTAN, build upload-sync, support Kiosk Level 2 — all contradicted by the v3.7 PRD/Data-Arch
rate_limit_attempts table doesn't exist — they need a decision
No TTS provider/voice selected — they can't build render-route-audio
No FCM payload schema — they can't build the trigger or the tablet receiver consistently
Custom-access-token-hook setup is not in any migration — they'd build a staging environment without it and wonder why every query returns empty
The pair-device step 6a query is ambiguous — they may ship the always-false bug
The render-route-audio function isn't designed for partial-failure / concurrent-edit semantics
No mock-GPS strategy — they can't exercise the state machine without a real bus

These are not stylistic. They are real questions the documents do not answer. The campaign closed seven structural gaps and opened a smaller number of new ones, several of which are concentrated around the new audio pipeline. The new pipeline looks like one bullet point in the changelog but is the largest single piece of work in the package and the most underspecified.
