## What PDS Is

A legally-regulated (UK PSVAR 2023), two-surface product: an **Android tablet app** (`pds-android`) that gives compliant audio + visual passenger information on rail-replacement buses, and a **Next.js dashboard** (`pds-dashboard`) where operators author routes and manage their tablet fleet. Both share a **Supabase** backend; audio is pre-rendered server-side via Google Cloud TTS. Pilot customer: a small bus company. See `PROJECT-HISTORY.md` for how it was built.

## Decision Ledger (standing decisions in force)

**Compliance rules (inviolable; every announcement-touching change inherits them):**
1. **Co-equal visual** — the screen flash and text overlay for a regulated announcement fire regardless of `audio_enabled`; a silent tablet still shows them. Any audio-mute must gate *only* the audio, never the visual.
2. **Asymmetric undroppable locking** — a regulated announcement interrupts a non-regulated one; a non-regulated one never interrupts; regulated-vs-regulated drops the later. A legally-required announcement is never silently lost.
3. **Event-index vs approached-index discipline** — the announced/passed stop and the approached stop are distinct indices; audio and boundary logic key on *approached*, event logging on *announced*. Terminus emits null, never clamp-to-last.
4. **≥22mm physical text** — passenger text is sized by physical measurement (calibrated) and never truncates below the floor; it grows line count instead.

**Working disciplines:**
5. **Deployed-shape audit before touching any deployed surface** — audit the actual deployed function/RPC/schema shape, don't trust the spec. Has caught real defects repeatedly (latest: 2026-07-09 — `generate-pairing-code`/`enqueue-render-job` are `verify_jwt: true` unlike the other six; a blanket `--no-verify-jwt` redeploy would have silently changed their auth posture).
6. **Plan-mode-first** — for any build, produce a plan and get it reviewed before editing; plan-mode review is a real gate, not a rubber stamp.

**Announce-on-departure model (added 2026-07-16; owner-decided through plan review + glass testing):**
31. **The next-stop announcement fires on DEPARTURE from the previous stop, not on arrival at it.** GPS stop detection is arm-only on arrival (entering a stop's radius sets a tagged departure gate, announces nothing, holds the displayed next stop); "Next stop: X" + the `current_stop_index` advance fire when the bus **departs** the previous stop (exits its radius). So the hero + tube-map hold "Next stop: X" through the whole approach and while stopped at X, flipping to X+1 only on departure (audio + visual in lockstep — co-equal visual, ledger #1). This is the Reg 9 "on-departure" model (gov.uk blesses both on-departure and on-approach; matches the frozen Compliance-Mapping-Matrix Reg 9(2)). Load-bearing sub-decisions: **arrival is arm-only**; the **terminus** fires completion on the arrival edge (the bus never departs it) via a **boolean** `gpsTerminusArrival` flag — deliberately a boolean, NOT a third index, so Rule 18's announced-vs-approached two-index framing is untouched; the **look-ahead advances ONE stop** (a late catch-up), not two; journey start primes `current_stop_index = 1` + an `AnnounceOnDepart(stop 0)` gate so the **origin is never announced as its own next stop**. **Informational-audio queue (Rule 19 refinement):** the first "Next stop" fires ~2 s after start and collided with the route-and-destination announcement → non-regulated announcements now use a **single-slot latest-wins queue** (park behind another informational one and play when it finishes; still drop behind a regulated one; a regulated announcement wipes any queued informational). Rule 19's inviolable regulated guarantees are untouched. Rejected alternatives: the two-cue "Next stop X" + "This is X" idea (Reg 9 is one requirement, not two), and the on-approach variant. **Robustness hardening (added 2026-07-17, glass-verified; the two previously-open items are now RESOLVED).** (a) **Geofence temporal hysteresis** (`46697b2`) — an actionable transition (arrive / look-ahead / depart) is acted on only after it persists `CONFIRM_FIXES=3` consecutive qualifying fixes (`MAX_FIX_GAP_MILLIS=6s` continuity guard); `confirmDecision` wraps the *untouched* `decideStopDetection`, the departure-gate state IS the accrual memory, and a mid-accrual NoOp is *refuting* when accurate (reset) but *held* when coarse (the compliance-safe direction — a jittery fix never wipes a legit accrual, so it can only bounded-delay, never drop; termination is backstopped by the stationary auto-timeout). `K=1` disables it byte-for-byte. Kills the looping-route early look-ahead AND the symmetric single-fix jitter-departure. (b) **H&R timing is compliant and UNCHANGED** — START at the last scheduled stop before the section (Reg 11(2)(a) mandates "at the last scheduled stopping place prior"; moving it to the first H&R stop would BREAK compliance), END on departing the last H&R stop; only the START *wording* moved "now entering"→"approaching" (`bc70f73`, Reg 11(1) forewarning). (c) **Coarse-GPS "Weak GPS" warning** (`6d26f78`) — a per-fix detector (no watchdog) warns the driver when fixes arrive but are too coarse to detect the current stop(s) for `COARSE_THRESHOLD_MILLIS=45s`, the silent-journey gap GPS-lost misses (it keys on fix *absence*); the pure `isStarvedFix` single-sources `passesAccuracyGate` and mirrors the detector's armed/disarmed gate branches (correct in the origin-priming window); non-dismissible driver-only amber, hidden while "No GPS" shows, off the announcement path. All three thresholds are glass-tunable and confirmed appropriate this session.

36. **The tube map shows the live position, derived from the existing departure gate — and it never animates.** `StopDetectionState.pendingDeparture` is non-null exactly when the bus is inside a stop's radius, already ledger-#31 hysteresis-confirmed, so it is flow-backed (same field → the observable `gate` mirror cannot drift) and the band reads from it. **No new detection, no new geofence**: a separate 5–10 m "at the stop" radius was proposed and **rejected** — Rule 6 discards fixes whose accuracy exceeds the radius and real bus GPS is commonly 10–30 m, so it would have failed exactly when the bus was at the stop, and it would have disagreed with both the announcement (which fires on exiting the stop's own radius) and the hero. If the fill ever reads too early the lever is that stop's dashboard-authorable `proximity_radius_meters`. Three sub-decisions, each glass-earned:
    - **The at-stop rule is index-relative, not gate-tag-relative** (`atStopIndexFor`: the gate's stop counts only within ±1 of `current_stop_index`). A tag rule (`AnnounceOnDepart` = at a stop) was designed first and **refuted in plan review** — the interpreter deliberately sets `SilentReArm` on terminus arrival, and the band is exposed ~1.5 s between overlay-clear and the end screen, so it would have read "in transit to the terminus" immediately after the termination announcement. The ±1 window also fixes the origin-priming and mid-route-start offsets, rejects an arbitrary `jumpTo` and a diversion skip-walked landing, and **structurally guarantees the filled node is adjacent to `current`** — it can never land outside the FR-AT-21 window view.
    - **Exactly one element is highlighted, and it is always the live position**: an enlarged solid disc at the stop the bus is at, or the heavier highlighted active segment while moving. **The next stop gets no treatment of its own** — a hollow ring was tried and glass-rejected as clutter competing with the at-stop disc; it is identified by its bold label and the segment running into it, and lights up only on arrival.
    - **"Passed" keys off a reached frontier, never `current_stop_index`** (`TubeMapGeometry.reachedIndex`). The current index names the stop being *approached* and runs one ahead of a standing bus, which dimmed the untravelled segment out of the bus's own stop at journey start and after a manual advance. Nothing ahead of the bus may carry the passed grey.
    - **No animation on the passenger surface.** The original sketch asked for light moving along dashed lines; dashes are unavailable (Rule 20 reserves them for hail-and-ride), and beyond that a pulse would have been the first perpetual animation there — motion is a scarce attentional resource already allocated to the regulated flash and the amber warning markers. `ACTIVE_SEGMENT_STROKE_DP` is the salience lever; the `build3-gps` TODO is retargeted at a real ~30 s position tick. **Only real position data earns motion on this surface.**
    - `DetectionEffects` gains **no third index** (ledger #31's boolean precedent; Rule 18 untouched), and the journey UI **combines** the gate with the Room-sourced index into one `TubeMapUiState` rather than collecting them independently — they propagate at different speeds and would transiently render the exact mismatched pair the feature exists to distinguish.

**Deployment footguns proven this session (added 2026-07-18, fifth session):**
39. **Three silent-failure modes in the render/deploy path, each now with a named check.**
    - **The version-collision trap.** `enqueue-render-job` mints the audio version from `updated_at`. A re-render that does NOT move `updated_at` overwrites the *same* Storage path, leaves `routes.audio_version` unchanged, and the tablet's missing-file-only downloader therefore fetches **nothing** — the fleet keeps playing stale audio while the dashboard reports success. **Re-render only by re-saving through the builder, and always assert `audio_version` increased and `audio_announcement_hash` changed.**
    - **`supabase db push` takes `--linked`, not `--project-ref`** (unlike `functions deploy`), and the link persists — it sat on **production** at this session's start. A wrong-environment migration is one forgotten `link` away. **Always `link` explicitly, then `db push --linked --dry-run` and read the environment and the migration list before confirming.**
    - **A new top-level dashboard page is served ANONYMOUSLY unless its path is added to `DASHBOARD_PATHS`** (`src/lib/supabase/middleware.ts`) — a path absent from that array is not a "dashboard path" and skips the auth chokepoint entirely, and the page simply renders. Page + allowlist + nav ship in ONE commit, and the gate is a logged-out request that must redirect to `/login`.
