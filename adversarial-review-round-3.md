I've read the seven documents end-to-end with the specific focus you asked for. What follows is what I found that isn't a re-discovery of rounds 1 and 2. I've ordered roughly by severity — the first group would cost real time on build, the middle group is underspecified or wrong but recoverable, the last group is operational / honest-uncertainty territory.
Severe — things that would block or burn time on the build
1. pg_boss in a Supabase Edge Function is an unvalidated architectural bet, and the docs speak about it as if it's a done deal
Where: Data-Arch §4.6 ("Worker: audio-render-worker Edge Function … invoked every minute by Supabase scheduled functions"); Data-Arch §11.2 and §12 listing it among Edge Functions; PRD §FR-WD-20; Data-Arch §4.6 "Installation and configuration."
Problem: pg-boss is, per its own README and npm page, "a job queue built in Node.js." v12+ requires "Node 22.12 or higher for require(esm)." Its canonical operation pattern is a long-lived process calling boss.start(), boss.work(), listening on Postgres NOTIFY, and holding advisory locks. Supabase Edge Functions are a Deno-based, short-lived, per-request runtime; Supabase's own docs explicitly say "Heavy long-running jobs should be moved to background workers." The plan tries to thread the needle by using boss.fetch + boss.complete from a scheduled Edge Function, but every invocation will: spin up a fresh Deno isolate, import pg-boss via npm: specifier, run boss.start() (which mutates pg-boss's internal schema and sets up timers/maintenance that assume long-lived process semantics), open a Postgres connection (without the connection pooler — see SUPABASE_DB_URL), then tear down. pg-boss's scheduled-job feature, its maintenance worker, its archive/expiry runners — all of those rely on the consumer being long-lived. They likely simply don't run, or run inconsistently. The advisory-lock-based fetch will work in isolation but the surrounding machinery is fighting the runtime.
Why it matters: Round 2 chose pg-boss specifically because "Postgres-backed … no new infrastructure: pg_boss creates its own tables inside the existing Supabase Postgres database. There is no separate queue service to deploy or pay for." That benefit evaporates if the worker has to be moved to Fly.io, Railway, or a Cloudflare Worker mid-build — which is exactly what Data-Arch §4.6 hints at as a future state ("the worker can be promoted to a dedicated long-running consumer (e.g., a Fly.io machine)"). The plan presents that as "if queue depth grows"; the more likely trigger is "the day we try to ship it." The cost is real: budget for it, ops complexity for it, deployment surface for it. None of this is in the plan or in the success-metric math.
The honest fix is not to alter the plan, it's to spend half a day actually wiring pg-boss from a Supabase Edge Function against a local Supabase instance and watching what breaks. If it works cleanly with boss.fetch/boss.complete and no boss.work-style scheduling required, great — the plan stands. If not, the audio pipeline needs a different substrate (Supabase's own pg_cron + a hand-written queue table, or Inngest, or Trigger.dev). Either way, deciding now is cheaper than discovering during Stage 3.

It is not a Supabase Edge Function and is deployed independently." CLAUDE-dashboard.md Rule 5 reinforces this: "Edge Functions and … the audio-render-worker (both of which run outside Next.js)" — phrasing the worker as distinct from Edge Functions.
But: PRD §NFR-R-07 (line 927) lists audio-render-worker among "Edge Functions." Data-Arch §4.6 (line 727): "Worker: audio-render-worker Edge Function." Data-Arch §11.2 lists it under "Edge Functions" with SENTRY_DSN_EDGE. Data-Arch §12 line 1650-1651 has SUPABASE_SERVICE_ROLE_KEY "All Edge Functions" required by audio-render-worker.
Why it matters: This is exactly the §13.7 propagation rule's job to catch, and it didn't. The dashboard builder reading CLAUDE.md gets the (probably correct, see finding 1) message: "the worker is separate, not our concern, deployed independently." The architect, reading PRD/Data-Arch, believes it's a scheduled Edge Function and may write prompts accordingly. The two views will diverge at the first Stage 1 task that touches the render pipeline (probably the enqueue-render-job Edge Function call from the route-save Server Action) because the dashboard builder will reasonably ask "where does the worker live?" and CLAUDE-dashboard.md's answer conflicts with what the architect believes. This is the meta-failure mode of round 2 reappearing in v3.8.
3. CLAUDE-android.md Rule 17 contradicts PRD NFR-R-07 and Data-Arch §11.2 on Sentry PII
Where: CLAUDE-android.md Rule 17 (line 292): "PII is stripped (no operator_id, no device_id beyond a coarse install identifier, no location)."
PRD §NFR-R-07 (line 927): "Breadcrumbs include diagnostic identifiers (device_id, route_id, current_stop_index) but exclude operator names."
Data-Arch §11.2 (line 1610-1612): "device_id is included because it is purely a diagnostic identifier and is essential for correlating crashes with the affected device in the fleet view; it is not personal data."
Why it matters: Rule 17 explicitly forbids what NFR-R-07 explicitly requires. The Android builder reading CLAUDE.md will scrub device_id from breadcrumbs; the dashboard's per-device Sentry drill-down (FR-WD-23 wants to correlate journey summaries with crashes, NFR-R-07 says diagnostic identifiers including device_id are present) will fail. The builder's PR will look correct against Rule 17 and wrong against NFR-R-07, and only the architect will know. Reconciling on device_id either way is fine; the contradiction is the problem.
The "coarse install identifier" wording is also under-defined — the Sentry Android SDK has its own concept of a per-install identifier (installation_id), which is distinct from device_id. Whether Rule 17 means "use Sentry's default install ID" or "scrub device_id from breadcrumbs but keep it as a tag" is unclear.
4. The local persistence location for the tablet's own audio_enabled is undocumented, and the flip-detection algorithm in §7.2 step 8 depends on it
Where: Data-Arch §7.2 step 8: "the tablet also re-reads its own devices row and compares the freshly synced audio_enabled against the value held immediately before this sync."
Problem: There's no Room devices table (the Room schema in §5 has only routes, route_stops, journey_events, journey_state, sync_metadata, journey_skipped_stops, journey_summaries_pending — no devices). SharedPreferences (§6.2) has no audio_enabled key. EncryptedSharedPreferences (§6.1) has no audio_enabled key. There is nowhere for "the value held immediately before this sync" to live persistently.
Why it matters: A Stage 2 builder writing the sync algorithm will hit this within the first hour. The fix is small — add a SharedPreferences key, or a Room single-row table, or stash it on sync_metadata — but the choice has ripple effects (where does the audio downloader read it from? where does the audio manager read it from?). With nothing in the plan, the builder will pick one and the architect may want a different one. This is a Case 2 (PRD §13.4) "missing detail" that the planning suite should have closed — particularly because §7.2 step 7's audio_enabled guard, on the same page, also reads "the local device's audio_enabled value from the most recently synced devices row" without saying where that's persisted.
5. A terminally-failed render takes a route out of service for the entire fleet, and the operator may not notice for up to 14+30 minutes
Where: PRD §FR-AT-28 (journey-start audio gate), Data-Arch §6.4 (gate logic), Data-Arch §4.6 (5 retries with 30/60/120/240/480s backoff = ~14 minutes to terminal failure), PRD §FR-WD-13 (route list shows red badge but operator must be looking at the dashboard).
Problem: Walk the sequence. Operator edits a route at version N+1 at 17:00. Worker retries fail terminally at ~17:14, sets audio_render_status='failed'. No FCM fires (correctly). Tablets see failed on next sync trigger — could be up to 30 minutes later via the WorkManager periodic. The tablet's journey-start gate (Rule 11 condition 1) is now closed: audio_render_status='failed' blocks the gate regardless of files present. The tablet has the version-N audio files on disk still (the cleanup is route_version-keyed and N hasn't been deleted) but the gate hardcodes "files at current route_version," and the current version is N+1, which never got rendered. So the local files for N are dead weight: present, but never consulted, because the gate looks at the wrong directory.
Total window in which the fleet has lost the route: up to ~14 minutes (render attempts) + up to 30 minutes (sync propagation) + however long until the operator notices the red badge on their route list and clicks "Re-render audio" + another render cycle.
Why it matters: This compounds with several other v3.8 mechanisms. There's no driver-side recovery path — the driver cannot acknowledge "I accept silent operation just for this journey" because that would (correctly per Reg 12(1)(b)) be a compliance failure. There's no fleet manager alert — no email, no FCM-to-dashboard notification (FCM is only to tablets), no Slack-style integration described. Just a red badge that the operator might see if they happen to be on the route list view. For a rail-replacement operator running a Sunday-evening shift with the dashboard user at home, this could mean an entire Monday-morning service running without audio on routes that were edited Sunday night.
Compare with the previously-working v3.6 design where any render failure left the previous TTS output in place. The version-keyed paths fixed real race conditions (round 2 task 1) but introduced this one. The plan doesn't acknowledge the trade-off.
6. journey_state.diversion_invoked_at_any_point is referenced in §7.8 but does not exist in the §5.5 schema
Where: Data-Arch §7.8 step 2, in parenthesis: "If the diversion was cleared mid-journey via 'Diversion end,' that already cleared the table; in that case diversion_invoked should be tracked via a journey_state.diversion_invoked_at_any_point boolean — see implementation note below."
Problem: §5.5 journey_state schema has columns id, route_id, current_stop_index, journey_started_at, is_active. No diversion_invoked_at_any_point. The "see implementation note below" implementation note is also not present in the document. The journey summary's diversion_invoked metric is therefore broken in exactly the case the parenthetical flags: a diversion that was started and then ended mid-journey will produce diversion_invoked = false in the summary, because journey_skipped_stops is cleared on "Diversion end" and there's no boolean retaining the fact.
Why it matters: This is a frozen-document gap that a builder will have to invent around. The fix is trivial — add a column to journey_state and clear it at journey start — but the plan presents the existence of the column as known, and it's not. The journey summaries feature was a round-2 addition (decision #37) and this is the kind of detail that round-2 missed at task close-out.
7. The custom access token hook can fire before the operators row exists, on the very first operator session
Where: Data-Arch §3.1 (signup flow: trigger fires AFTER INSERT on auth.users, creates the operators row + sends email). Data-Arch §3.4a: hook fires "on every token issuance — including login, refresh, and Admin API session creation."
Problem: Supabase Auth signup is a single API call that returns a session (a JWT + refresh token) to the dashboard. The session JWT issuance is the first token the hook fires for. The AFTER INSERT trigger on auth.users and the token-issuance hook are both side-effects of the same signup call; their ordering relative to each other is not contractual. If the hook fires first (or the trigger transaction hasn't yet committed when the hook reads operators), the SELECT in the hook returns no row, and the first JWT lacks the operator_id claim. Every operator-scoped RLS query on that first session silently returns empty until the operator logs out and back in (forcing a fresh token issuance, by which time the operators row is present and the hook stamps the claim correctly).
Why it matters: This is the documented "RLS-silently-returns-empty" canonical failure mode (Data-Arch §12 step 4, both CLAUDE.md gotchas), but caused by a race rather than missing hook registration. A new operator's experience on signup is "I signed up, I'm logged in, but my dashboard is totally empty — nothing works." The fix is straightforward (have the hook idempotently look up the operators row, or move the operators-row creation to a synchronous part of the signup flow) but the planning suite hasn't acknowledged the race exists.
This also affects pairing. The pair-device Edge Function creates an anonymous auth user, then inserts the devices row, then calls auth.admin.createSession (or equivalent). The hook fires on session creation. If createSession is called before the devices row INSERT commits in the same transaction (or if pair-device creates the user via the Admin API in one transaction and the devices row in another), the device's first session JWT could also lack operator_id. The plan's ordering in §4.2 steps 6–10 implies a sequence but doesn't specify transactional boundaries.

10. FR-AT-50 (Deregister Device) wipes incomplete credentials
Where: PRD §FR-AT-50 line 676: "wipes all local route data, removes the device JWT, and returns the app to the first-run setup screen."
Problem: Compare with FR-AT-04 terminal-failure handling (line 369-370): "the cached JWT, refresh token, and device secret are wiped from EncryptedSharedPreferences." FR-AT-50 mentions only the JWT. A deregistered device's storage retains the refresh token and device secret — both of which would still authenticate against a recover-device call if the dashboard hadn't yet flipped activation_state='inactive' (which it does in the same path, so the race is small) and both of which are exactly the credentials an attacker with a stolen-and-deregistered device would want.
The intent is clearly "wipe everything," and CLAUDE-android.md Rule 12-equivalent commentary in NFR-S-07 implies full wipe. But the PRD FR — the spec the builder is implementing — only names the JWT. A literal-reading builder ships a partial wipe.
11. FR-WD-12 "Generate return route" doesn't say who enqueues the audio render for the newly-generated return route
Where: PRD §FR-WD-12 line 255-261.
Problem: Initial generation: "creates a separate route entity with the same stops in reverse order" — no mention of audio rendering for the new entity. Re-generation (line 259): "triggers audio re-rendering for the return route" — phrased passively. Audio rendering is fired by enqueue-render-job (FR-WD-08, Data-Arch §4.4 "Audio rendering" paragraph), and that Edge Function is called by the dashboard, not by any database trigger. So the dashboard's "Generate return route" Server Action must explicitly call enqueue-render-job for the new return route's ID after the route entity is created — exactly the same way the route-save action does. The doc doesn't say this. A builder implementing FR-WD-12 will likely figure it out, but the omission is a "should have been caught" — particularly because the round-2 task 1 audio-pipeline overhaul was supposed to make the dashboard's audio-enqueue obligations explicit.
12. The two-version Storage retention doesn't survive a fast-editing operator
Where: Data-Arch §4.7 (keep two most recent versions per route).
Problem: The justification ("Two-version retention gives a tablet a recovery window if it synced the route metadata just before a new save") assumes one new save between the tablet's last sync and the cleanup. An operator iterating a route 4 times in 30 minutes between, say, 02:30 and 02:55 produces versions N+1, N+2, N+3, N+4. At 03:00 UTC the cleanup deletes everything except N+3 and N+4. A tablet that synced metadata at 02:35 has route_version=N+1 in Room and tries to download from {operator_id}/{route_id}/N+1/... — 404. The tablet logs AUDIO_FILE_MISSING and the route shows "Audio not ready" until the next sync trigger, which pulls the new metadata pointing at N+4. So it self-heals on the next sync, but: (a) the tablet briefly has a route it can't start a journey on, and (b) the journey-start gate blocks any driver who happens to be looking at the route during that gap.
Acceptable, probably, given how rare fast iteration is — but the plan asserts the two-version retention is sufficient without naming the assumption.
13. 30/60-day auto-deregistration is in tension with the heartbeat's OEM-best-effort caveat
Where: PRD §1.4 and Data-Arch §10 (auto-deregister at 60 days of last_seen_at silence). Data-Arch §7.7 OEM caveat ("a tablet that is powered off, fully backgrounded, in aggressive doze mode, or managed by a hostile OEM may show offline … This is acceptable and documented behaviour").
Problem: Consider a seasonal-route tablet powered on but backgrounded by the OEM for 9 months between summers. The foreground heartbeat doesn't fire because the app isn't foregrounded; the WorkManager background heartbeat is best-effort and likely throttled to nothing by a hostile OEM (this is the very case §7.7 names as acceptable for fleet-view purposes). last_seen_at falls 60+ days behind. The daily cleanup flips activation_state='inactive'. The operator returns at the start of the next season, powers up the tablet to start a journey, and finds it must re-pair — because the system mistook "OEM throttled" for "tablet is dead."
The plan acknowledges OEM unreliability for fleet-view purposes and uses heartbeat fidelity for auto-deregistration; it doesn't reconcile the two. A "two days of failed recover-device attempts" or "explicit operator decommission" signal would distinguish "system thinks tablet is dead" from "tablet has been actively rejected" — but the current rule is purely time-based on last_seen_at.
14. The Reg 12(1)(b) consistency argument doesn't cover the multi-tablet-on-one-bus visual disagreement case
Where: Compliance Matrix Reg 12(1)(b), particularly the closing line "audio-visual content parity across the fleet." Compliance Note 4 (Rear-facing wheelchair spaces): "their journey progress is approximately synchronised."
Problem: Two tablets on one bus run independent GPS state machines. Tablet A (front, audio_enabled=true) and tablet B (rear, audio_enabled=false) each progress their own journey_state.current_stop_index from independent GPS fixes. They will drift in any of the following circumstances: a fix that satisfies one tablet's accuracy gate but not the other's (different GPS chipsets in the two tablets); a fix one tablet receives in a window the other misses; a manual stop-advance the driver does on tablet A but can't do on tablet B (the rear tablet has no driver controls — but even if it did, the driver only touches one).
Regulation 12(1)(b) requires audio and visual to be consistent. The audio comes from tablet A's speaker. The visual the rear passenger sees comes from tablet B. If tablet B's display says "Next stop: Hexham" while the audio (from A) is announcing "Next stop: Carlisle," the rear passenger experiences inconsistency.
Compliance Matrix Reg 12(1)(b) covers the audio-bytes-identical question (good) but its "audio-visual content parity" line elides this. Note 4 mentions "approximately synchronised" but the regulation doesn't admit approximations. The honest framing is: the software's Reg 12(1)(b) compliance argument depends on a 1:1 bus-to-audio_enabled=true-tablet mapping AND it depends on all tablets-on-one-bus having sufficiently agreeing GPS fixes — and the second condition isn't software-enforced. This is the same family as the "honest framing" rewrite of Reg 12(1)(b)'s audio_enabled enforcement (round 2 task 2), one level deeper.
For an MVP that ships to a single pilot bus run by a personal contact, this is fine and pragmatically invisible. As a compliance matrix entry intended to survive regulatory scrutiny, it's incomplete.
15. The Reg 13(4) "BLOCKING WORK" baked into a frozen document is half a planning failure away from invalidating the voice lock
Where: Compliance Matrix Reg 13(4): "BLOCKING WORK — voice locked to en-GB-Neural2-B; frequency verification required pre-deployment."
Problem: The voice lock is presented as decided (an "inviolable rule"), but the verification is a TODO that could fail. If the spectrum-analyser pass on en-GB-Neural2-B shows energy outside 300Hz–3000Hz beyond the sibilants-allowance, the row's own text says: "a different Google TTS voice must be selected, the voice lock updated in code, and the verification re-run — this is a Case 1 re-planning trigger." The plan has therefore baked a single audio verification step into both the frozen Compliance Matrix and the Data-Arch lock as an act-of-faith. If it fails, the lock is wrong and the suite goes to v3.9 before the build has even started.
The pragmatic step is to run the verification now — render a sample sentence through Google TTS via the public API (which is identical to what the worker will eventually do), spectrum-analyse it, and update CONTEXT.md with the result. Doing this in five minutes before declaring v3.8 frozen is much cheaper than triggering a Case 1 event later.
Operational / honest-uncertainty findings
16. No driver-side recovery path when audio is "not ready" on a Monday morning
The journey-start audio gate (Rule 11) is a hard block. A driver showing up at 06:00 to start a 06:30 service finds the route says "Audio not ready." The only recovery is: the operator (who is the fleet manager, not on the bus) hits "Re-render audio" on the dashboard, the worker runs successfully, the tablet syncs. If the operator isn't reachable, the driver has no path forward except calling them. This is correct from a compliance standpoint (silent operation is non-compliant). It's a real operational hole that the plan should at least name — perhaps with explicit advice to fleet managers about "save and verify the day before, not the morning of."
17. No staging environment story
CLAUDE-dashboard.md mentions Vercel preview deploys for branches. No document says preview branches deploy against a staging Supabase project, a separate Supabase project, or — by default — the same production project. The default Vercel + Supabase setup uses one Supabase project. A PR's preview deploy with a routes.delete() mutation in a Server Action would mutate production routes. The dashboard's RLS gives some protection (only the authenticated operator's routes), but the build's testing story is ambiguous. Stage 1 is the time to decide.
18. The Sentry free-tier math is asserted, not shown
PRD §NFR-R-07 and Data-Arch §11.2 both claim 5,000 errors/month is "sufficient at projected fleet size." That's about 165/day. With three surfaces (Android + dashboard + Edge Functions) each sending exceptions, ANRs, server-action errors, and Edge Function errors, even a 20-tablet pilot could easily breach this — every AUDIO_FILE_MISSING event the Sentry Android SDK auto-reports, every transient pg_boss retry, every 404 from Storage during the version-keyed race window. The plan doesn't show calculations, doesn't say what gets sampled, doesn't say what counts toward the quota. If quota is exceeded mid-month, Sentry silently drops events — and the system admin loses observability exactly when something is going wrong. The "Sentry fails open" framing makes this sound benign; in practice, silent error loss in a regulated product is the opposite of operational visibility.
19. Setup checklist (Data-Arch §12) has order dependencies that aren't called out
Steps 1–7 read as a list. Several have ordering dependencies the list doesn't surface: step 4 (custom access token hook registration) must precede the first dashboard signup or that signup will hit the race in finding 7; step 2 (FCM credentials) must precede the first audio-render-worker deployment or the worker's FCM dispatch will error; step 7 (Sentry DSN provisioning) must precede any code that initialises Sentry, which on Android is Application.onCreate — i.e., before the first build. A new system admin reading the checklist alone could miss these. A short "Order matters in the following ways" paragraph would help.
20. The Re-Render Audio action (FR-WD-21) has no deduplication
Hitting it twice rapidly enqueues two pg_boss jobs at the same route_version. Both jobs pass the staleness check (the routes.updated_at matches). Both compute the same hash and find the files already present (from the first run), so no actual TTS spend — but each job still acquires advisory locks, performs database UPDATEs (audio_render_status='ok'), and dispatches FCM. Tablets receive two FCM messages, run two redundant syncs. Wasted but harmless. Worth noting because the FR-WD-21 button text and feedback don't tell the operator "don't click twice" — and operators bored of a 60s render are exactly the population that clicks twice.

Honest assessment
Round 3 had to clear a higher bar than rounds 1 and 2, and the findings reflect that. Setting aside the four stale cross-references (findings 8, 9, 10, the JWT-vs-secret wipe — all small) and the operational concerns (findings 16–20 — real but lower-priority), the substantive list is:

One genuine architectural risk (pg_boss in Deno Edge Functions, finding 1) — high enough that I'd verify before starting Stage 3.
Three direct v3.8-state contradictions between documents (findings 2, 3, 11) — exactly the failure mode §13.7 was supposed to prevent. The propagation rule worked for some changes and not others; one (finding 2) is significant enough that the dashboard and Android builders will reach different conclusions on day one of integration.
One blocking missing-detail (finding 4, local audio_enabled persistence) — small fix, but a Stage 2 builder hits it within an hour.
One unfinished spec (finding 6, diversion_invoked_at_any_point) — small.
Two compound-failure modes that the plan doesn't acknowledge (finding 5, terminal render bricks the route; finding 7, custom-hook race on first session) — both real, both rooted in v3.8-era additions, both recoverable.
One compliance argument gap (finding 14, multi-tablet visual consistency) — almost theoretical at MVP scale, real if you scale or get audited.
One pre-deployment task masquerading as a frozen decision (finding 15, Reg 13(4) verification) — fixable in five minutes today.

That's roughly 8–10 substantive findings against the >50 from rounds 1 and 2 combined. The yield is clearly down. If you ran a round 4 against the post-round-3 documents, my honest expectation is that you'd find: more stale cross-references, a few more underspecified details that emerge from compound scenarios, and zero new architectural problems. The architecture is settled in a way it wasn't after round 1; round 2's additions are largely correct in shape and wrong only in detail.
The single most consequential outstanding question is finding 1 — pg_boss in Deno. If that works (verify on a half-day spike), the plan is buildable as written modulo the detail-level fixes. If it doesn't, the audio pipeline goes back to the drawing board, and a fair amount of v3.8's confidence collapses with it. I'd resolve that before declaring v3.8 frozen-for-build.
