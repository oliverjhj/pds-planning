**Decisions made:**
- **Scope widened to the pilot's location, against the prior session's plan.** 2a had scoped 2b to the relationship alone on the grounds that the company is "never named anywhere". That is true but insufficient: a fresh audit found the pilot identifiable by **location** — the operating area, two real route numbers and a NaPTAN area prefix, all present in HEAD and in four commit messages. Since the whole purpose of the scrub is to protect the company's identity, naming-only would have left the job half done.
- **The owner's own home town scrubbed too, on a second pass.** Initially left in scope-out. Reconsidered when it became clear it sits ~20 miles from the pilot's operating area, so leaving it re-anchored the real geography and partially undid the location scrub. 10 occurrences, both in history-only files.
- **Delete and recreate the GitHub repo, never force-push.** A force-push leaves unreachable pre-scrub commits fetchable by direct SHA on GitHub for an indeterminate period. For a private repo about to go public that is the entire exposure being scrubbed. Done twice — once for the main rewrite, once for the home-town pass.
- **Supabase project refs deliberately left unscrubbed** (both prod and staging — a staging ref existed and had never been noted). They are not secrets, every client request carries the ref, and the prod ref appears in a Sentry issue title that the infrastructure shot films. Also deliberately kept: the tablet serial, the Vercel deploy URL, the Sentry org slug and monitor ID, and production entity UUIDs.
- **Stale self-referential SHAs accepted, not chased.** A second rewrite pass to renumber them would double the rewrite surface to improve prose nobody audits. A README note at Phase 6 covers it instead.
- **`literal:` rules only, never `regex:`.** `git-filter-repo` keeps literals and regexes in **two separate lists** and applies all literals first regardless of file order, so mixing them makes ordering non-obvious. Every target was a fixed string, so literals also removed all backslash-escaping hazards.
- **A standing vocabulary rule added to the workspace `CLAUDE.md`.** This repo is now publication-bound: anything written into it from here ships publicly, so a future close-out could silently reintroduce the scrubbed terms. The rule covers file contents *and* commit messages, and names what is deliberately **not** scrubbed so nobody over-corrects.

**Banked / open:**
- **The prior audit was wrong in six places, all corrected by re-measurement.** 59 commits not 58; the relationship in 17 commits across 6 paths, not 16 across 5; Firebase counts 176/154 not 165/146; the username leaked 5× not 9×; **six** commit messages carried identifiers, not one; and the phrase in the closure commit message is *not* line-wrapped mid-phrase as claimed. A staging Supabase ref and one further place name (a real street used as a test stop) had been missed entirely. **Lesson: re-measure a prior session's counts before building rules on them.**
- **Three bare-token rules would have silently corrupted unrelated text**, each caught by measuring before running: one route number also appears inside a real `pds-android` commit SHA (14×), the NaPTAN prefix also appears inside a hex colour in the design-language table (15×), and the username is a substring of the owner's GitHub handle, which is inherently public. All three were defused by anchoring; assertions that the SHA and the hex colour still occur exactly 14 and 15 times are part of the verification.
- **The backslash trap is real and bites silently.** The rules file needed four literal backslashes for one path form; a quoted heredoc still delivered two, because a transport layer halved them. Caught by an `od -c` byte check before the rewrite ran. Fix: the file is now generated by a Python script using `chr(92)`, so no backslash passes through a shell. The same hazard makes shell-argument verification untrustworthy — `git grep` with a backslash pattern returns a **false PASS**. All counting was done in Python against the object store.
- **Two file-format traps, either of which leaks silently with no error:** a UTF-8 BOM becomes the first bytes of rule #1's match string and disables it; a blank line becomes a rule matching the empty string, inserting the replacement between every byte of every file. Both are checked before the tool runs.
- **The `--dry-run` step is what made this safe.** It writes the filtered stream without importing, so every byte of the outcome was reviewable while the repo was still pristine.
- **One commit lost its GPG signature.** The root commit was a signed GitHub web-UI commit; `git-filter-repo` strips signatures because it cannot re-sign rewritten objects. Tree, author, committer, timestamp and message are byte-identical. It was the only signed commit of the 59. Inherent to any history rewrite.
- **`git-filter-repo` remapped commit-message hashes**, correctly leaving 53 unmappable short hashes alone — they are `pds-android` / `pds-dashboard` SHAs, not this repo's, and they must stay valid.
- **Backups retained** outside the repos at `C:\Users\dev\Documents\pds-scrub-2026-07-30\`: a `--mirror --no-hardlinks` clone and a full folder copy, both still holding the original pre-scrub content, plus the rule files as the record of exactly what changed. **That folder must never be copied anywhere shared** — the rules file necessarily contains the original strings.
