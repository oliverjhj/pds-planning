# Session: 2026-07-16 — Model 2: announce next stop on departure, not arrival

**What changed:** Reworked the Android GPS next-stop announcement timing from the arrival edge to the **departure edge** (the "model 2" the owner chose during pilot testing). Previously, entering a stop's proximity radius was treated as "arrived at that stop" and immediately advanced `current_stop_index` and announced the *following* stop — so while the bus was still approaching stop X, the display/audio had already flipped to "Next stop: X+1". Now: **arrival is arm-only** (holds the display), and **"Next stop: X" fires when the bus departs the previous stop** (exits its radius); the display holds "Next stop: X" through the approach and while stopped at X, flipping on departure. This matches the owner's Compliance-Mapping-Matrix Reg 9(2) and their verbatim description ("100 m after it sets off from Green you hear 'Next stop: Marford Library'"). Implemented via a **tagged departure gate** (`DepartureGate.AnnounceOnDepart` vs `SilentReArm`) on `StopDetectionState`; new decisions `ArriveCurrent` (arm-only) / `DepartCurrent` (announce+advance) / `ArriveLookAhead` (advances one, a late catch-up); terminus keys on a new `gpsTerminusArrival` boolean (a boolean, NOT a third index — Rule 18's two-index framing preserved); journey start primes `current_stop_index = 1` + an `AnnounceOnDepart(stop 0)` gate so the origin is never announced as its own next stop. **No composable/ViewModel changes** — the hero and tube-map already read `current_stop_index`, so audio + visual stay in lockstep (co-equal visual preserved/improved). Two follow-up fixes landed from glass testing (below). Full plan in `~/.claude/plans/warm-petting-wall.md`.

**Decisions made:**
- **Announce-on-departure is the model (new ledger #31).** Arrival arm-only; announce + advance on departure; display holds through arrival, flips on departure; terminus fires on the arrival edge (bus never departs it) via a boolean flag; look-ahead advances one stop. Reg 9-compliant (gov.uk blesses both the on-departure and on-approach models; this is the on-departure one, and matches the owner's own compliance doc). Chosen over the two-cue "Next stop X" + "This is X" idea (rejected — Reg 9 is one requirement, not two; a second bundled audio file per stop was disproportionate) and over the on-approach variant (owner's concrete description was the departure one).
- **`gpsTerminusArrival` is a boolean, not a third index** — deliberately so Rule 18's "two sibling indices" (announced vs approached) framing stays intact.
- **First-next-stop audio: latest-wins queue, not drop.** The first "Next stop" fires ~2 s after journey start (departing the origin) and collided with the route-and-destination announcement still playing → the informational drop-overlap (Rule 19) dropped it. `AnnouncementPlayer` now gives informational (non-regulated) announcements a **single-slot latest-wins queue**: behind another informational one they park and play when it finishes; behind a **regulated** one they still drop, and a regulated announcement **wipes** any queued informational (a next-stop can never trail a termination/chime). Rule 19's inviolable regulated guarantees are untouched — only informational-vs-informational changed from "drop" to "queue-latest". Owner approved this ("option 1").
- **Terminus disarm fix:** `ArriveCurrent(last)` was clearing the gate (re-arming), so it re-fired `ArriveCurrent(last)` on every fix while parked at the terminus (a live run logged 10 `STOP_ANNOUNCED` for a 6-stop route). Now disarms with a `SilentReArm` gate → parked fixes are NoOps.

**What's next (FIRST thing next session — owner-requested):** **Robustness of the geofence against looping routes.** Detection is straight-line (haversine) distance from the GPS point to each stop, with strict N-then-N+1 progression + a one-stop look-ahead (Rule 5, needed for GPS-missed-stop recovery). On a Lockito path that **loops back / doubles over** (the owner's test path revisited Marford Green and swung crow-flies-close to Shops), the bus enters a later stop's radius early and the look-ahead correctly-but-undesirably fires ahead. This is inherent to GPS geofencing, but **some real rail-replacement routes may loop**, so we need a robustness pass / decision (e.g. does sequential progression + per-stop radius suffice, or do we need path-aware guarding?) before the pilot. Also observed: starting the journey **before** the mock bus is parked on the origin makes the first departure fire immediately (real-world: driver starts at the origin, so minor — but note it).
