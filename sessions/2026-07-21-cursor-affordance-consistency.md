# Session: 2026-07-21 — Cursor affordance consistency across the dashboard

**What changed:** A short, self-contained dashboard session with no feature work. The owner noticed that some clickable things in the dashboard show the hand cursor and some don't, and asked whether that was a deliberate button-vs-navigation distinction or just inconsistency. It was inconsistency, and the diagnosis was worth more than the fix: **nothing in the stack sets a cursor for interactive elements at all** — Tailwind v4's preflight (verified in `node_modules/tailwindcss/preflight.css`, v4.3.0), `shadcn/dist/tailwind.css`, and `globals.css` all leave `button` alone — so every control fell back to the browser UA stylesheet, which sets `cursor: pointer` for `a[href]` and nothing else. The hand/arrow split therefore tracked "was this built as an anchor", which correlates with navigate-vs-act only by accident. The visible symptom was pairs of identical-looking controls disagreeing: **"New Route"** (a `Link` wearing `buttonVariants`) got the hand while **"Re-render all"** beside it did not, and the same mismatch appeared between Edit/Back and Re-render/Delete in the route-detail metadata bar. Three ad-hoc `cursor-pointer` patches had already accumulated (status-badge popover trigger, device-name rename button) as one-off responses to the same root cause — the tell that this deserved a central fix.

A full audit was done before planning: every interactive element in `src/` classified, and — load-bearing — the **actual rendered element** for each base-ui primitive checked in `node_modules` rather than assumed. That check changed the fix: `Switch` renders `<span role="switch">` and `DropdownMenuItem` renders `<div role="menuitem">`, so a `button`-only selector would have silently missed the `audio_enabled` fleet toggle and every menu action.

Fixed centrally in `globals.css`, **not** by editing generated `ui/*` (Rule 16). Two rules, and the split between them is the mechanism:
- **Base layer** — `button`, `[role="switch"]`, radio/checkbox inputs, and `label:has(> input[type=radio|checkbox])`. Base layer is deliberate: the utilities layer outranks it, so `cursor-grab` on the route-builder drag handle and `cursor-default` on an inactive control still win. The `:has(> input)` scoping keeps the 16 stacked `<Label for>` form labels out of it — a hand over "Email address" would be its own new oddity.
- **Unlayered**, scoped to `[data-slot="dropdown-menu-*"]` — the generated component hard-codes a `cursor-default` **utility**, and CSS cascade layers mean utilities beat `@layer base` regardless of specificity, so unlayered is the only way to reach menu items without editing the generated file.

One carve-out was needed in the other direction: base-ui renders `TooltipTrigger` as a real `<button>`, and both instances in `device-table.tsx` (status dot, android_id) are hover-only — they take an explicit `cursor-default` so the new global default doesn't advertise a click that does nothing.

Also cleaned up: a stray workspace-root `.playwright-mcp/` directory (24 console-log and snapshot files accumulated since 11 July across sessions — outside all three repos, so untracked by anything and covered by no `.gitignore`), and the dashboard `CLAUDE.md` verified-against stamp, which was four commits stale.

**Decisions made:**
- **Dropdown menu items take the hand (owner-decided).** shadcn sets `cursor-default` on menu items on purpose, mirroring native OS menus, and leaving it was a defensible option. Owner chose consistency: these are actions (Sign out, Re-render audio, Acknowledge), not OS-menu rows, and the whole point of the change was removing "why not this one?". This is what forced the unlayered second rule.
- **`globals.css` is the single source; do not patch per-component.** Recorded as a new Rule 16 bullet naming both carve-outs (drag handle `cursor-grab`, the two hover-only `TooltipTrigger`s) and the disabled-exclusion mechanism. The rule exists specifically so the next instinct to add a local `cursor-pointer` has somewhere to land instead — three such patches had already accumulated.
- **NOT synced to the three design-system copies (ledger #27), deliberately.** Assessed and rejected on three grounds: the sync rule exists to stop *drift* between hand-maintained copies, and cursor behaviour cannot drift (one CSS rule, enforced by the cascade, inherited automatically by every future control); it is **dashboard-only** and the design language is deliberately two-surface (no cursor exists on a touch tablet), so it would have been the first entry applying to half the product; and the Claude Design cards are static rendered HTML that cannot show a cursor, so that copy would carry unverifiable prose — exactly the kind of entry that rots. Rule 16 is the better home and is read every dashboard session. Owner agreed after asking whether the design system would benefit.
- **Verify the rendered element, not the component name.** Checking base-ui's `useRenderElement` calls in `node_modules` is what caught `Switch` → `<span>` and `MenuItem` → `<div>`. A reasonable-looking `button, [role="button"]` selector would have shipped with the fleet audio toggle and every menu action silently unfixed.

**Verified:** `lint` / `typecheck` / `build` all green. Beyond that, two levels the change specifically needed: (1) the **compiled stylesheet** was inspected to confirm cascade placement — base rules inside `@layer base`, `.cursor-grab` inside `@layer utilities`, the menu rule unlayered — since that ordering *is* the mechanism and asserting it beats assuming it; (2) a **runtime computed-style pass** via Playwright against the real stylesheet over all 12 element shapes, including the four that must NOT change (drag handle `grab`, tooltip `default`, plain label `default`, number input `text`) and three disabled states (disabled button `default`, disabled menu item `default`, real disabled Switch `not-allowed` via its own utility). One row first read FAIL — a bare `<span role="switch">` computed `auto` where `default` was expected — which was a wrong test expectation, not a defect; re-run with the component's actual classes it gave `not-allowed`. Deployed to production (`dpl_5erd…`, READY, aliased on `pds-dashboard.com`) and **owner-confirmed working on the live site**. No hardware verification applicable — nothing regulated, no Android surface, no schema, no Edge Function, no deployed backend shape touched.
