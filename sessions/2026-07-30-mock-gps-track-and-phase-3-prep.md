**Decisions made:**
- **Accuracy is written into the GPX per point, not set in Lockito's UI.** Lockito 3.8.2 ships its import profiles as JSON assets; the **"Lockito v2"** profile is selected by the file's `creator` attribute matching `^Lockito 2.0$` and is the only built-in GPX profile that extracts accuracy at all (the generic "GPX standard 1.0" profile maps it to null). Writing accuracy into the file therefore **closes the long-standing Lockito accuracy gotcha by construction** rather than working around it — the "configuration to use on newly added parts" control is never consulted. The `creator` attribute is load-bearing: change it and the file silently falls back to the profile that ignores accuracy.
- **Straight-line legs, never road-following — a correctness decision, not convenience.** The road route from Victoria to Knightsbridge runs through **Hyde Park Corner, which is stop 2 on this route**. Under the Rule 5 two-stop look-ahead a road-following mock would enter stop 2's radius while stop 1 was still current, mark Knightsbridge passed-without-detection, and announce the remainder one stop out of step. Straight legs clear every look-ahead stop by **at least 595 m** against 200 m radii; the generator recomputes and prints that check on every run rather than trusting a comment.
- **The track is generated, not hand-drawn.** Hand-drawing cannot place points on the exact stop coordinates and is not reproducible between takes, and reshoots mean rebuilding the whole stack. The generator is a deterministic Python script with three profiles, held in the owner's vault alongside the emitted GPX.
- **Timings chosen against the detection layer, not by eye:** 36 km/h cruise (20 s inside each 200 m radius, about 10 fixes where 3 are needed to confirm), **120 s pause at the origin** so the simulation is already feeding fixes at stop 0 when the journey is started — a fix inside stops 1–4 on the first post-start fix would raise the FR-AT-11 "starting here?" prompt — 25 s at each intermediate stop, and 120 s at the terminus so fixes keep flowing through termination and the end screen.
- **The credential-bearing rows were deliberately left out of the dump.** `devices`, `device_pairing_codes` and `rate_limit_attempts` carry an FCM token, a device secret hash and an IP address; a permission guard blocked writing them to a file, and the guard is right. Recorded judgement: they are **not worth preserving** — the device row describes a tablet that will be wiped, the pairing code is used and expired, and a restored system mints new ones. `naptan_stations` (375,730 rows, 77 MB) was excluded as public re-importable reference data.
- **The APK artefact is `prodDebug`, not a release build.** The project has no `signingConfigs` block, so a release build would come out **unsigned and uninstallable**. `prodDebug` is also exactly the variant that runs on the tablet and appears in the video. Reported rather than worked around — nothing here needs a Play-signed artefact.
- **Announcement audio is taken from source for the edit, not miked off the tablet.** `adb screenrecord` captures no audio at all, and the video's most important shot is about audio and visual arriving together. All 14 WAVs (the seven rendered RR1 files plus the bundled chime, termination, hail-and-ride and diversion announcements) were extracted at source quality; the 500 ms flash gives an exact sync point in the edit.

**Verified:**
- **Deployed-shape audit of Lockito's own file format before writing any of it.** The import-profile JSON gives the XPaths but records no units. A probe file with deliberately unambiguous values established them: `lockito:speed` is **km/h, not metres per second** (the initial assumption was wrong and would have produced a run 3.6× too slow), `lockito:accuracy` is metres, `lockito:pause` is seconds. Proved arithmetically — an imported 612 m leg displayed `00:03:40` against a `10 km/h` chip, and 612 m at 10 km/h is 220 s.
- **The filming track, read back from Lockito after import:** leg chips `Free · 36 km/h · 10 m · Recorded`; the Dorchester→Marble Arch leg `611 m / 00:01:01` against a computed 61.3 s; whole run `5 km / 00:13:57` against a computed 14.1 min.
- **Live fixes, read from `dumpsys location` rather than reasoned about.** Stationary at the origin: `Location[fused 51.495258,-0.144559 hAcc=10.0 vel=0.0 mock]` — exactly the stop coordinate, and `vel=0.0` confirms the first-waypoint pause holds the simulation at the start, so no lead-in leg is needed. In motion: `hAcc=10.0 vel=10.0 bear=300.47` — 10 m/s is exactly 36 km/h, and bearing 300.47° matches the computed origin→stop-1 heading of 300.5°. **hAcc 10 m against a 200 m accuracy gate clears it by a factor of twenty.**
- **Rule 11 journey-start gate will pass:** the tablet holds `route_announcement.wav` plus `stop_0`–`stop_5.wav` at audio version `1785359329458`, matching the production row exactly.
- **No hand-applied production schema changes — verified three ways, having previously only been owner-confirmed.** (a) The migration ledger matches the 24 committed files exactly, in order. (b) All **67 deployed objects** were cross-referenced against the migration SQL; seven were not found literally — six are Postgres's auto-generated names for inline `CHECK` constraints, each traced back to its clause, and the seventh, `rls_auto_enable`, is Supabase platform provisioning, proven by its definition being **byte-identical on staging**, where no migration creates it either. (c) A full schema digest over columns, defaults, function bodies, policy expressions, constraints, indexes, triggers and RLS flags is **identical on production and staging** — 178 object lines, both `73bbd75ed50291c42fa124b2bc4a2c16`. Two independently provisioned environments driven only by the committed migrations cannot match byte for byte if either had been hand-edited. **The backend is fully reconstitutable from git; teardown loses nothing.**
